# Альфа.Навигатор — конкурсный демонстрационный прототип

Работающий демонстрационный **сквозной кредитный конвейер** для малого бизнеса. Клиентский кабинет, финансовый симулятор, банковская очередь, модель правил, альтернативное предложение, уточнение данных и журнал событий. **Только синтетические данные, никаких реальных кредитных решений.**

## Запуск

Требуется Docker с Compose.

```bash
docker compose up --build
```

Откройте http://localhost:8000. Демо-пароль по умолчанию: `alfa-demo-2026`; при входе выберите роль. OpenAPI: http://localhost:8000/docs. Проверки: `/api/health` — процесс жив, `/api/ready` — база отвечает и схема актуальна (иначе `503`).

Локально без Docker: `pip install -r requirements-dev.txt && uvicorn app.main:app --reload`.

Контейнер работает от непривилегированного пользователя. Если volume `navigator_data` остался от версии, где процесс работал от root, пересоздайте его: `docker compose down -v`.

## Деплой на Vercel через GitHub Actions

Демо: https://alfa-navigator-gamma.vercel.app

Приложение работает на Vercel как одна Python-функция: [api/index.py](api/index.py) импортирует FastAPI-приложение, а [vercel.json](vercel.json) направляет на неё все пути. Деплоит только GitHub runner, автодеплой из Git-интеграции Vercel выключен (`git.deploymentEnabled: false`).

Пайплайн [.github/workflows/ci.yml](.github/workflows/ci.yml):

1. **test** (SQLite и Postgres): pytest, проверка снимка `docs/openapi.json`, затем приложение запускается на runner'е и проходит smoke-тест [scripts/smoke.py](scripts/smoke.py) с полным сценарием (вход → заявка с повтором по `Idempotency-Key` → скоринг → принятие сохранённого предложения), и проверку потока изменений: первое сообщение должно прийти сразу, иначе предупреждение о буферизации.
2. **e2e**: браузерные тесты на Playwright (Chromium) против запущенного приложения: основной сценарий клиент → банк → клиент, поздний ответ по прежней заявке не подменяет карточку, двойной клик по «Подать заявку» создаёт одну заявку, команда из устаревшей карточки получает 409 и карточка обновляется, в режиме двух экранов банк видит новую заявку, а клиент — скоринг без перезагрузки, тур по демо проходит все 8 шагов. При падении скриншоты и трассировки сохраняются в артефакт `e2e-results`.
3. **audit**: `pip-audit` по полностью зафиксированному `requirements.txt`; известная уязвимость останавливает деплой.
4. **deploy** (после test, e2e и audit): `vercel pull` → `vercel build` → `vercel deploy --prebuilt`, затем smoke-проверка задеплоенного URL. Push в `main` выкатывает production, PR из этого репозитория выкатывает preview. На production smoke только читает: `/api/ready`, вход и чтение очереди из базы. Полный сценарий с записью идёт на preview, когда у preview своя база (переменная репозитория `PREVIEW_DATABASE_ISOLATED=true`). Ручной запуск: Actions → CI/CD → Run workflow.

Разовая настройка:

1. Создайте проект на Vercel и привяжите его локально: `npx vercel link`. ID появятся в `.vercel/project.json`.
2. Создайте токен: Vercel → Account Settings → Tokens.
3. Добавьте в GitHub (Settings → Secrets and variables → Actions) секреты `VERCEL_TOKEN`, `VERCEL_ORG_ID` (поле `orgId`) и `VERCEL_PROJECT_ID` (поле `projectId`).
4. Задайте в Vercel → Project → Settings → Environment Variables для Production **и** Preview свои `DEMO_CLIENT_KEY`, `DEMO_BANK_KEY`, `DEMO_CLIENT_PASSWORD`, `DEMO_BANK_PASSWORD` (для preview лучше другие значения), а пароли продублируйте в GitHub Secrets для smoke-проверки. С демо-значениями из репозитория или без `DATABASE_URL` приложение в production и preview не запустится. Локально значения по умолчанию работают.
5. По желанию: Vercel закрывает уникальные URL деплоев авторизацией (Deployment Protection). Production проверяется по публичному алиасу, а smoke-проверка preview пропускается с предупреждением. Чтобы preview тоже проверялись, включите Protection Bypass for Automation и положите его значение в секрет `VERCEL_AUTOMATION_BYPASS_SECRET`.

**База данных.** Если задан `DATABASE_URL` (или `POSTGRES_URL`), приложение работает с Postgres, иначе с SQLite по пути `DB_PATH`. На Vercel к проекту подключён Neon из Vercel Marketplace (бесплатный тариф, регион `iad1`). Локальный запуск, Docker и тесты по умолчанию используют SQLite. Проверить базу и версию схемы: `GET /api/ready`.

Схема ведётся версионируемыми миграциями (таблица `schema_migrations`). По умолчанию они применяются при старте под advisory lock; с `MIGRATE_ON_START=0` их выполняют отдельным шагом `python -m app.main migrate` (для Neon — через direct endpoint, приложение работает через pooled), а `/api/ready` до этого отвечает `503`.

**Изоляция preview.** Preview не должен писать в базу production: иначе заявки и демо-данные из PR попадают в публичное демо. Включите в интеграции Neon в Vercel создание отдельной ветки базы для каждого preview-деплоя (Vercel → Integrations → Neon → Preview branching; [ветки Neon](https://neon.com/docs/introduction/branching)) или задайте для Preview отдельный `DATABASE_URL`. После этого добавьте переменную репозитория `PREVIEW_DATABASE_ISOLATED=true` (Settings → Secrets and variables → Actions → Variables), чтобы smoke на preview проходил полный сценарий. Проверка: заявка и демо-данные, созданные в preview, не появляются в production.

## Быстрый e2e-тест

**Два экрана.** Ссылка **Два экрана** в шапке (или адрес `/split`) открывает кабинет предпринимателя и кабинет банка рядом; в каждом окне свой вход. Выбор заявки общий: заявка, поданная или открытая в одном окне, сразу открывается в другом. Действие одной стороны появляется у другой за секунду, с уведомлением и подсветкой изменённой заявки. Так весь сценарий ниже проходит без переключения ролей. На узком экране окна переключаются вкладками.

**Тур по демо.** Кнопка **Показать сценарий** на `/split` (или ссылка **Пройти сценарий на двух экранах** на странице входа, адрес `/split?tour`) проводит одну заявку за 8 шагов: вход в оба окна → сценарий «Другие условия» → подача → заявка у банка → скоринг → ответ у предпринимателя → выбор варианта → итог. Тур подсвечивает нужный элемент в нужном окне и переходит дальше сам, когда шаг выполнен; кнопка **Сделать за меня** выполняет шаг вместо зрителя. Пароли вводит человек: тур их не знает.

1. В клиентском кабинете введите данные кофейни или нажмите один из готовых сценариев над формой: «Одобрение», «Другие условия», «Уточнение», «Ручное решение» — под кнопками появится ожидаемый результат. В симуляторе меняйте сумму и срок: платёж и нагрузка считаются по базовой ставке 22%, график остатка — на 12 месяцев от первого платежа, после погашения кредита платёж по нему не списывается.
2. Войдите как предприниматель и отправьте заявку на 5 млн ₽ при потоке 240 тыс. ₽/мес. и существующих платежах 30 тыс. ₽. Под формой показывается предварительная оценка по тем же правилам, что и скоринг банка (`POST /api/precheck`, ничего не сохраняет). Если условия не проходят, у предложенных вариантов есть кнопка **Подать с этими условиями**. После подачи открывается карточка заявки: этапы, чей сейчас ход и до какого срока.
3. Выйдите и войдите с ролью **Кабинет банка** — выберите ту же заявку. Очередь можно фильтровать по статусу, сумме, компании или номеру, по умолчанию срочные заявки сверху. Для заявок, ждущих банк, показывается время до конца SLA (24 ч, меняется переменной `BANK_SLA_HOURS`); нарушения подсвечиваются. Вкладка **Аналитика** (`GET /api/analytics`) показывает воронку, исходы предложений, частые причины отказов, ставки одобренных заявок и метрики SLA: долю ответов банка в срок, среднее и медианное время ответа, текущую очередь.
4. Нажмите **Провести скоринг**. Демомодель рассчитает оценку и, если запрошенные условия не проходят, предложит варианты: меньшую сумму на тот же срок или ту же сумму на более долгий срок. Нагрузка оценивается по базовой ставке 22%, а итоговая ставка зависит от балла: от 85 — 18%, от 70 — 20%, от 65 — 22%; ниже 65 баллов одобрить можно только вручную, под 26%. Одобрение и контрпредложение действуют 7 дней (`OFFER_VALID_DAYS`), затем получают статус «Предложение истекло»; банк может продлить предложение, в том числе истёкшее.
5. Переключитесь в кабинет предпринимателя. Изменения другой стороны приходят сразу (индикатор **Онлайн**, см. «Живые обновления»), есть кнопка **Обновить**. Карточка показывает, как сложилась оценка (исходный балл и вклад каждого фактора), блок **Как получить одобрение** и варианты условий с платежом, переплатой, собственными баллом и нагрузкой. Выберите вариант: принимаются ровно выданные условия, даже если тарифы с тех пор изменились. Наверху карточки остаются согласованные условия, запрос и исходная оценка — ниже. У каждого варианта есть помесячный график платежей (`POST /api/schedule`) с выгрузкой в CSV. Заявку можно отозвать до принятия условий, а отклонённую, отозванную или истёкшую — изменить и подать заново со ссылкой на прежнюю.
6. После скоринга сотрудник банка может **одобрить или отклонить заявку вручную** с обязательной причиной. Автоматический результат сохраняется в поле `decision`, ручное решение — в `explanation.manual_override` и в историю событий; ручное одобрение выпускает новое предложение.
7. Создайте новую заявку и запросите уточнение из банка, отметив нужные поля: поток, выручку, платежи по долгам, просрочки. Клиент заполняет только запрошенные поля, изменения попадают в историю, затем заявку можно оценить заново.
8. Перезапустите контейнер — данные сохраняются в Docker volume.

В графике платежей можно рассчитать досрочное погашение: сумма, месяц и что уменьшать (срок или платёж); показывается экономия на процентах.

**Живые обновления.** Окно подписывается на `GET /api/changes/stream` (server-sent events): сервер раз в секунду (`STREAM_POLL_SECONDS`) проверяет журнал событий и присылает новые изменения. Поток живёт 8 секунд (`STREAM_SECONDS`, меньше лимита функции Vercel `maxDuration: 10`), затем окно переподключается со своего курсора и ничего не теряет. Поток читается через `fetch`, поэтому токен идёт в заголовке, а не в адресе. Если прокси буферизует поток и первое сообщение не пришло за 5 секунд, окно переходит на опрос `GET /api/changes?after=<курсор>` раз в 3 секунды. Скрытая вкладка соединение не держит. Общий опрос раз в 30 секунд остаётся страховкой.

**Демо-данные.** В кабинете банка кнопка **Заполнить демо-данными** (`POST /api/demo/seed`) создаёт 26 синтетических заявок с историей за последние дни: все статусы, нарушения SLA, истёкшие предложения, ручные решения, все ступени ставки. Их номера начинаются с `DEMO`; повторное нажатие пересоздаёт их, **Удалить демо-данные** (`DELETE /api/demo/seed`) удаляет только их, настоящие заявки не затрагиваются. Отключается переменной `ENABLE_DEMO_SEED=0`.

Для сценария одобрения уменьшите сумму до 1 млн ₽. Для сценария отказа включите просрочки и запросите большую сумму. Сброс отключён по умолчанию. При необходимости на локальной машине установите `ENABLE_DEMO_RESET=1` и выполните `POST /api/demo/reset` с банковским токеном.

## Структура

- `app/main.py` — сборка FastAPI-приложения: журнал запросов, формат ошибок, статика, подключение обработчиков; `python -m app.main migrate`.
- `app/settings.py` — настройки из переменных окружения; `app/storage.py` — Postgres или SQLite, миграции, журнал событий.
- `app/policy.py` — правила скоринга demo-rules-v1; `app/schedules.py` — платёж, график погашения, сезонный сценарий.
- `app/workflow.py` — состояние заявки, переходы с проверкой версии, выданные предложения; `app/schemas.py` — модели API.
- `app/handlers/` — HTTP-обработчики: заявки, аналитика, расчёты, вход и проверки, живые обновления (`live.py`); `app/demo.py` — демо-сценарии.
- `app/static/index.html` и `app/static/app.js` — интерфейс двух ролей; `app/static/split.html` и `app/static/tour.js` — режим двух экранов и тур по демо.
- `docs/architecture.md` — архитектура, границы, data model, state machine, API, тест-кейсы.
- `docs/openapi.json` — выгружаемая спецификация OpenAPI (также доступна `/openapi.json`).
- `tests/` — тесты сценариев, конкурентных команд, правил и контракта API.
- `requirements.in` — прямые зависимости; `requirements.txt` — полный зафиксированный набор для деплоя; `requirements-dev.txt` — тесты.
- `docker-compose.yml` — повторяемый запуск и volume.
- `THIRD_PARTY_NOTICES` — компоненты и моки.

## Допущения

- Нагрузка оценивается по базовой ставке 22%, ставка предложения 18–26% зависит от балла; ставки вымышлены и **не соответствуют ставкам или политике Альфа-Банка**.
- Скоринг — детерминированные правила `demo-rules-v1`; система не претендует на оценку реального кредитного риска.
- Реестр компании, бюро кредитных историй, подписание договора и выдача денежных средств **не подключены**; данные клиент вводит самостоятельно, просрочки — синтетический флаг.
- Есть **только демонстрационное** разделение ролей по статическим токенам. Это не промышленная идентификация или полноценный аудит. **Никогда не вводите реальные ПДн.** Подробности в `docs/limitations.md`.
- В следующей итерации: авторизация пользователей и компаний, отдельная таблица политик, пагинация очереди и агрегаты в базе, rate limiting.

## Для жюри

Здесь важно, что действия банка реально меняют клиентскую заявку, а состояние и объяснение сохраняются. Дополнительные функции не заменяют основной e2e-процесс. Проект запускается без платных API и без доступа к корпоративной инфраструктуре.

## Проверка и материалы сдачи

```bash
python -m pip install -r requirements-dev.txt
python -m pytest -q
python scripts/export_openapi.py   # обновить docs/openapi.json после изменения API

# браузерные тесты
python -m pip install -r requirements-e2e.txt
python -m playwright install chromium
python -m pytest e2e
```

Обновление зависимостей: правьте `requirements.in`, затем `uv pip compile requirements.in --python-version 3.12 --no-header -o requirements.txt` и проверьте `pip-audit --no-deps -r requirements.txt`.

- `docs/scenarios.md` — подробные сквозные и негативные сценарии.
- `docs/limitations.md` — ограничения и честные допущения.
- `docs/postman_collection.json` — коллекция запросов.
- `.github/workflows/ci.yml` — тесты, smoke на runner'е и деплой на Vercel при push/PR.
- `docs/openapi.json` — снимок API; CI и тесты проверяют, что он совпадает с `/openapi.json`.

**Для отправки:** загрузите проект на GitHub *со своей историей коммитов*, зафиксируйте tag/commit hash до дедлайна, при приватном репозитории откройте доступ `alfa-hack-2026`. При возможности разверните публичное демо; сайт конкурса и конкурсный аккаунт не подключены к этому архиву.
